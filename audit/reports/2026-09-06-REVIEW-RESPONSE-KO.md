# 검수 의견에 대한 판단과 반영

검토일: 2026-09-06. 검수자의 1차 지적 10개와 후속 반박 4개를 기존 문서·보관한 감사 자료·공식 문서에 대조했습니다. 이 답변은 사이트 수정 완료 보고가 아닙니다.

## 먼저 인정할 부분

제어 가능 범위를 실행의 선행 조건으로 명시하지 않은 점, 네이버라는 제목에 비해 본문 범위가 불분명한 점, 성능 반려선과 개선 지표·일정이 없는 점은 기획의 누락입니다. 기존 문서가 canonical을 바꿀 수 있다고 암묵적으로 전제할 수 있다는 지적도 수용합니다.

네이버의 실제 유입 채널을 확인해야 한다는 반론은 문서 제목·본문의 불일치를 해소하지 못합니다. 앞선 답변은 이 핵심을 충분히 겨냥하지 못했습니다. 보고서 제목을 **Google SEO·AEO 개선 기획 보고서**로 바꾸고, 별도 트랙으로 **네이버 서치어드바이저 기반 웹사이트 기술 검증**을 명시했습니다. 네이버 운영 전반의 최적화를 약속하지 않습니다.

| 네이버 내용 부족 | 제목·본문 불일치 수용 | Google 본문과 네이버 웹사이트 기술 검증 트랙 분리 |

| 복수 title 원인 유형 없음 | 수용. 공개 출력의 형태와 관리자 기원을 구분 | 143위젯 분류표와 공통 수정 절차 추가 |

## 후속 반박에서 수용·수정할 부분

### 1. canonical은 의존성 게이트가 맞습니다. 다만 분기를 수정합니다

자동 생성은 공식 안내로 확인되지만, 사이트별 수정 가능·불가는 미검증입니다. 기존 태그를 대체할 수 있을 때만 직접 수정안을 진행합니다. 추가만 가능할 때는 두 번째 canonical을 넣지 않습니다. [아임웹 안내](https://imweb.me/qna?mode=faq&q=71763)

다만 “태그 편집·추가 모두 불가하면 4단계를 삭제하고 관측만 한다”는 결론은 이릅니다. 내부 링크·사이트맵·주소 이동의 제어 여부는 독립된 질문입니다. B와 C 모두 해당 수단을 확인한 뒤 결정해야 합니다. 설명문 수정도 canonical과 독립적이므로 4A·4B로 분리했습니다.

“canonical 2개면 항상 둘 다 무시”도 확정적으로 쓰지 않습니다. Google은 복수 선언을 무시할 가능성을 경고합니다. 위험을 피해야 한다는 결론은 같지만, 가능성을 보편 법칙으로 바꾸지는 않습니다. [복수 canonical 주의사항](https://developers.google.com/search/blog/2013/04/5-common-mistakes-with-relcanonical), [대표 주소 지정 수단](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)

### 2. 네이버는 범위를 명시한 별도 기술 트랙으로 처리합니다

기존 내용이 제목의 약속을 뒷받침하지 못한다는 지적을 수용합니다. 소유확인·수집 접근·페이지 정보·사이트맵·해당 RSS·제출 상태·색인 관찰을 독립 목록으로 추가했습니다. 플레이스·블로그·광고·리뷰 운영은 제외합니다.

이는 “네이버까지 최적화 완료”가 아니라 앞으로 수행할 제한된 기술 범위입니다. RSS는 유효한 피드와 콘텐츠가 있을 때 검토하며 전 사이트에 새 피드를 의무 생성하지 않습니다. [네이버 제출 기준](https://searchadvisor.naver.com/guide/request-feed)

### 3. 출력 형태로 지금 공통 설계하는 것은 맞습니다

설계를 시작하는 데 관리자 템플릿 공유 여부가 반드시 필요한 것은 아닙니다. 139/143, 약 97.2%의 문서 묶음형을 기준으로 공통 절차를 설계했습니다. 작업 단위도 77페이지가 아니라 **143위젯**으로 명시했습니다. 정확히 집계하면 문제 위젯이 2개 이상인 페이지는 **22개**입니다.

반면 **시작 태그의 종류가 같음 → 제거해도 되는 모든 태그가 같음**은 성립하지 않습니다. 이 분류는 태그 존재 여부를 기준으로 했을 뿐 body 속성·스타일·스크립트 의존성의 동일성을 증명하지 않았습니다. 최소 title 제거를 공통 출발점으로 삼고, head 전체나 body 속성을 일괄 제거하는 것은 별도 검증 대상으로 둡니다.

즉 공통 설계를 미루지 않되, 설계 재사용과 검증 없는 일괄 삭제를 구분합니다. [분류 수치·근거·수정 절차](TITLE-CAUSE-REVIEW-KO.md)

### 4. hreflang의 “항상 0%”와 “x-default 필수”는 수용하지 않습니다

우리의 소프웨이브 완료선은 5개 언어 전체의 자기참조·상호참조 검증입니다. 다만 이는 내부 완료 기준이며, Google이 부분적으로 유효한 관계를 처리하지 못한다는 뜻은 아닙니다.

Google은 일부 언어가 빠져도 서로 참조하는 관계는 처리할 수 있다고 명시합니다. 상대 페이지에 이미 올바른 역참조가 있다면 영어 쪽 수정 하나로 그 관계가 정상화될 수도 있습니다. 반대로 역참조가 없다면 해당 관계는 미완료입니다. 실제 양쪽 출력을 확인해야 하며 “영어 단독 수정이면 정의상 항상 0%”라고 단정할 수 없습니다.

x-default 역시 기본 이동 대상을 지정하는 **권장 항목**이지 필수 조건이 아닙니다. 이번에는 신규 지정 보류, 운영 대상 승인 시 일관 적용으로 정했습니다. 따라서 완료 조건은 “5언어 자기·상호참조 검증 + 선택한 x-default 정책 준수”입니다. [Google 다국어 공식 기준](https://developers.google.com/search/docs/specialty/international/localized-versions)

## 추가로 고친 실행 계획의 문제

이전 상세 계획에는 관리자 before·rollback 원문을 공개 저장소에 커밋하는 것으로 읽히는 경로가 있었습니다. 이를 제거하고 비공개 백업 ID로 연결하도록 바꿨습니다. 아직 만들지 않은 검사기의 예상 PASS를 실제 검증처럼 혼동할 수 있는 절차도 정리했습니다.
